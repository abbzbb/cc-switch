# 4.7 Combo Virtual Models

A Combo packs several real `{slug}/{model}` targets into one virtual model `combo/{id}`. Requests to that id follow the Combo strategy. They do **not** depend on the app-level failover switch.

> The proxy must be running, and the app you call (Codex and/or Claude) must be taken over. Every target slug must exist on that app. To pin a single card, use [4.6](./4.6-model-routing.md) instead of a one-target Combo.

## Where to configure

Open the **Proxy** panel while the proxy is running and find **Combo virtual models**.

| Field | Meaning |
|-------|---------|
| Combo id | Short name, e.g. `main`. Requests use `combo/main` |
| Strategy | `failover` or `round-robin` |
| Targets | One `provider/model` per line, optional `:weight` |

The list shows `combo/{id}`, the strategy, and a target summary. Click a row to edit; the trash icon deletes it.

## How to write targets

One target per line, or comma-separated:

```
kimi/k2
deepseek/deepseek-v4:1
packy/claude-sonnet-4-6:2
```

- Base form: `{routing_slug}/{upstream_model}`
- With weight: `{routing_slug}/{upstream_model}:{positive integer}`. Default weight is 1
- The slug must resolve to a card on the current app; the model is that card’s upstream id

## Strategies

### failover (default)

Try targets in order. After a hop exhausts its retries, move to the next target. The Combo path does this itself — you do not need [4.3 Failover](./4.3-failover.md) turned on.

Use this when one cheaper/faster card should go first, then a more reliable card.

### round-robin

Pick the **first hop** by weight. If that hop fails, the remaining targets are still tried.

Use this to share load across similar cards. Higher weight is chosen as the first hop more often.

## CLI

```bash
codex -m "combo/main" "Explain this code"
claude --model "anthropic/combo/main"
```

Claude Code shows `anthropic/combo/{id}`, same `anthropic/` prefix as a normal pin.

## Errors

| Situation | HTTP | Meaning |
|-----------|------|---------|
| No Combo with that id | 400 | e.g. `combo/foo` when only `combo/main` exists |
| Combo exists, but no target resolves on this app | 503 | Wrong slug, deleted card, or a different app is taken over |

The app-level failover queue does **not** take over these errors. Put the backup card in the Combo target list.

## Versus pin, pool, and app failover

| Request | Behavior |
|---------|----------|
| `kimi/k2` | Pin the Kimi card |
| Unprefixed `gpt-5.5` (several official cards) | Account pool, sticky session |
| `combo/main` | Combo strategy across the listed card/model pairs |
| Unprefixed + app failover on | On failure, switch the **whole card** (that card’s default model) |

A pin beats the pool. `combo/` is the Combo namespace, not a brand slug.

## Notes

- If any Combo exists, the `combo/` namespace is reserved. Do not set a provider routing slug to `combo`.
- Targets must be `slug/model`, not `anthropic/kimi/k2` (that is only the Claude Code display id).
- Changing a card’s slug does not rewrite Combo rows. Edit them in the proxy panel.
- Combo does not sign you in. Managed OAuth targets still need Auth Center login and a bound card.
