# 4.7 Combo 仮想モデル

Combo は複数の実在 `{slug}/{model}` を仮想モデル `combo/{id}` にまとめます。この id へのリクエストは Combo の戦略に従い、**アプリ級フェイルオーバースイッチには依存しません**。

> プロキシを起動し、使うアプリ（Codex / Claude）を接管してください。ターゲットの slug はそのアプリ上に存在する必要があります。1 枚だけ固定するなら [4.6](./4.6-model-routing.md) を使い、1 ターゲットの Combo は作らないでください。

## 設定場所

プロキシ稼働中に **Proxy** パネルを開き、**Combo 仮想モデル** を探します。

| 項目 | 意味 |
|------|------|
| Combo id | 短い名前。例 `main`。リクエストは `combo/main` |
| 戦略 | `failover` または `round-robin` |
| ターゲット | 1 行に 1 つの `provider/model`。任意で `:weight` |

保存後、一覧に `combo/{id}`・戦略・ターゲット要約が出ます。行をクリックして編集、ゴミ箱で削除します。

## ターゲットの書き方

```
kimi/k2
deepseek/deepseek-v4:1
packy/claude-sonnet-4-6:2
```

- 基本形：`{routing_slug}/{upstream_model}`
- 重み付き：`{routing_slug}/{upstream_model}:{正の整数}`。省略時は 1
- slug は現行アプリのカードに解決できること。モデルはそのカードの上流 id

## 戦略

### failover（既定）

設定順に試します。あるホップの再試行が尽きたら次のターゲットへ。Combo 自身が切り替えるので [4.3](./4.3-failover.md) をオンにする必要はありません。

安くて速いカードを先に、失敗したら安定したカード、という用途向けです。

### round-robin

重みで**最初のホップ**を選びます。失敗しても残りのターゲットは試します。

似たカードで負荷を分ける用途向けです。重みが大きいほど最初のホップに選ばれやすくなります。

## CLI

```bash
codex -m "combo/main" "このコードを説明して"
claude --model "anthropic/combo/main"
```

Claude Code では `anthropic/combo/{id}` です。

## 失敗時

| 状況 | HTTP | 意味 |
|------|------|------|
| その名前の Combo がない | 400 | `combo/foo` を書いたが `combo/main` しかない |
| Combo はあるが、このアプリで解決できるターゲットがない | 503 | slug 誤り、カード削除、別アプリの接管 |

アプリ級フェイルオーバーキューはこれらのエラーを引き継ぎません。予備カードは Combo のターゲットに書いてください。

## 固定・プール・アプリ級フェイルオーバーとの違い

| リクエスト | 動作 |
|------------|------|
| `kimi/k2` | Kimi カードを固定 |
| 接頭辞なし `gpt-5.5`（公式カード複数） | アカウントプール、セッション粘着 |
| `combo/main` | リスト上のカード/モデルを Combo 戦略で回す |
| 接頭辞なし + アプリ級フェイルオーバー | 失敗時に**カード全体**をキュー順で切り替え |

固定はプールより優先です。`combo/` は Combo 用名前空間です。

## 注意

- Combo が 1 件でもあると `combo/` は予約されます。プロバイダー slug を `combo` にしないでください。
- ターゲットは `slug/model` です。`anthropic/kimi/k2`（Claude Code の表示 id）は書かないでください。
- カードの slug を変えても Combo 行は自動更新されません。
- Combo はログインしません。マネージド OAuth ターゲットは認証センターでのログインとバインドが必要です。
